# Local Server GPU Bring-up & Ollama Stack — Setup & Implementation Report

**Date:** 2026-11-04
**System:** Laptop `pmpmt-ThinkPad-T15-Gen-2i` (Ubuntu, Pi v1.4.0, Node v24.21.0 via nvm); local server `192.168.1.60` = `pmpmt-B550-AORUS-ELITE-V2`, Ubuntu 24.04.4 LTS, kernel `7.0.0-42-generic`, Ryzen 5 5600X, 15 GB RAM, `GA106 [GeForce RTX 3060 Lite Hash Rate]` 12288 MiB; NVIDIA driver `595.99.02` (CUDA 13.2, compute 8.6); Ollama `0.40.14`
**Location:** `~/.ssh/config`, `~/.ssh/id_ed25519_lan-pmpmt{,.pub}`; CoS home `~/.pi/agent-cos-orchestrator-agent/cos-orchestrator-agent/` → `docs/runbooks/`, `docs/inventory/`, `docs/demos/`, `scripts/`; server → `/home/pmpmt/ollama-stack/`, `/home/models/ollama/`, `/etc/systemd/system/ollama.service.d/`, `/etc/apt`-managed NVIDIA packages

---

## Problem

Three connected gaps blocked "use the idle desktop on the LAN as a local AI box":

1. **No privileged access to the account that owns the data.** The agent could reach the server only as `pistore` (storage identity). `/home/pmpmt` is `drwxr-x--- pmpmt:pmpmt`, so its contents were unreadable — `Permission denied` on `~/Downloads`, which the user asked to list.
2. **The GPU did not work.** `nvidia-smi` had been failing since before this session ("couldn't communicate with the NVIDIA driver"). The previous runbook had recorded this as an open finding with no cause identified. Without it, any local model runs on CPU.
3. **No local LLM runtime.** Ollama was not installed, and the obvious install target — the default `/usr/share/ollama` — sits on the 73 GB root filesystem with only 30–33 GB free, against a ~25–30 GB default model set.

Goal: key-based access to `pmpmt@192.168.1.60`, a working GPU driver that survives reboot, and a tuned Ollama stack with its weights on the data partition rather than `/`.

## Investigation / Root Cause

### 1. Access: what the two identities can actually do

| Probe | Result | Consequence |
| --- | --- | --- |
| `ssh pmpmt@192.168.1.60` (before) | `Permission denied (publickey,password)` | no key, no password held by the agent |
| `ssh lan-storage 'sudo -n true'` | `SUDO_OK`, `uid=0(root)` | `pistore` carries `NOPASSWD: ALL` → the only escalation path |
| `sudo -n` as `pmpmt` | `sudo: a password is required` | `pmpmt` cannot be driven non-interactively |
| `sshd -T`-relevant config | `AllowUsers pmpmt pistore`, `PermitRootLogin no` | `pmpmt` logins are permitted; root is not |

So the key could be **installed** without the user's password, by appending to `/home/pmpmt/.ssh/authorized_keys` as root via `pistore`'s sudo over SSH — no console access needed.

### 2. GPU: the failure was a missing kernel module, not a broken driver

Diagnosis chain, each step narrowing the cause:

| Step | Command | Output | Reading |
| --- | --- | --- | --- |
| 1 | `nvidia-smi` | "couldn't communicate with the NVIDIA driver" | userspace present, kernel side absent |
| 2 | `mokutil --sb-state` | `SecureBoot disabled` | not a signing/MOK problem |
| 3 | `modinfo nvidia` | `ERROR: Module nvidia not found` | no module for this kernel at all |
| 4 | `journalctl -b -g nvidia` | `modprobe: FATAL: Module nvidia not found in directory /lib/modules/7.0.0-42-generic` | confirmed, reproducible at every login |
| 5 | `dpkg -l \| grep nvidia` | `nvidia-driver-570-open 570.211.01`, `linux-modules-nvidia-570-open-6.17.0-22-generic` | driver installed, **modules built for kernel 6.17.0-22** |
| 6 | `uname -r` | `7.0.0-42-generic` | kernel moved on after the driver was installed |
| 7 | `dkms status` | `dkms: command not found` | **root cause: no DKMS, so nothing ever rebuilt the module** |
| 8 | `apt-cache policy linux-modules-nvidia-570-open-7.0.0-42-generic` | empty | no prebuilt package exists for this kernel |

The decisive detail was step 5+7 together: an installed `nvidia-driver-*` metapackage is not evidence of a working module, because Ubuntu ships the module in a separate, kernel-pinned `linux-modules-nvidia-*` package unless DKMS is present.

### 3. Which driver series to install

| Candidate | Evidence | Verdict |
| --- | --- | --- |
| Reinstall `nvidia-driver-570-open` | DKMS candidate is `570.86.10`, userspace already at `570.211.01` | **rejected** — module/library version mismatch |
| `nvidia-dkms-570-open` alone | same 570.86.10 candidate | rejected for the same reason |
| Prebuilt `linux-modules-nvidia-570-open-7.0.0-42-generic` | not in the archive | impossible |
| **`nvidia-driver-595-open` (595.99.02)** | `ubuntu-drivers devices` already marked it *recommended*; ships `nvidia-dkms-595-open` + matching userspace | **chosen** |

Simulated first (`apt-get install -s`): a clean swap — 16 removed (all `-570` libraries plus the stale `6.17.0-22` module packages), 16 installed. No conflicting holds.

### 4. Storage: where weights may live

| Target | Free at the time | Verdict |
| --- | --- | --- |
| `/usr/share/ollama/.ollama/models` (default, on `/`) | 30 G | would leave ~0–5 G headroom after the default set |
| **`/home/models/ollama` (on `/dev/nvme0n1p7`)** | 323 G | **chosen** |

### 5. Thinking models break the kit's summariser

The kit's default chat models (`gemma4:12b`, `qwen3.5:9b`) are reasoning models: they emit into Ollama's `thinking` field. A request without `"think": false` spends its whole `num_predict` budget on reasoning and returns an **empty** `response`, which `summarize-doc.py` treated as failure (`RuntimeError: empty response from model`). Measured directly:

```
num_predict=120, no think flag  → eval 120 tok, response: "" , thinking: "Topic: Practical uses…"
num_predict=120, think:false    → response: "1. Quickly extracting key points…", 48.7 tok/s
```

## Architecture / Design Decisions

### 1. Two identities, deliberately split

| Alias | Account | Capability | Used for |
| --- | --- | --- | --- |
| `lan-storage` | `pistore` | `NOPASSWD: ALL` → root | system changes (driver, installs, key installation) |
| `lan-pmpmt` | `pmpmt` | home/data access; sudo needs a password | reading `~/Downloads`, running `ollama`, the summariser |

Keeping both means routine file work never runs with root in reach, while privileged work never needs the user's password. Alternative (single `pmpmt` identity) rejected: it would block every unattended system change. Alternative (ask the user for the password each time) rejected: it makes the agent useless for this class of work.

### 2. Escalation is explicit, not implicit

The report asks "who escalates" and answers with a rule, not a habit: privileged steps run as `ssh lan-storage 'sudo -n …'` and are documented as such in the runbook, so the user can see when root on that box is being used. All facts gathered for diagnosis were read-only.

### 3. Fix forward to 595 rather than patch 570

570 had a kernel-newer-than-module problem plus an unavailable DKMS version. 595 is the series the distro already recommends, brings a matching `nvidia-dkms` package, and builds against the running kernel. One `apt install` replaced the whole incoherent 570 stack instead of layering a 570.86.10 module under 570.211.01 libraries.

### 4. Prove it before rebooting

The module was loaded live (`modprobe nvidia`, `modprobe nvidia_uvm`) and `nvidia-smi` queried **before** the reboot, so the reboot verified persistence rather than hoping the build was sound — a reboot tests "does it autoload", not "did the build work".

### 5. Install in an order that never fills `/`

Install the runtime and a 274 MB embedding model first → relocate the weights directory to `/home` → *then* pull the 21 GB of chat models. Pulling first would have put ~21 GB on a 30 GB root filesystem and then required a 21 GB copy.

Two systemd drop-ins, non-overlapping by design:

| Drop-in | Owns | Written by |
| --- | --- | --- |
| `05-models-dir.conf` | `OLLAMA_MODELS=/home/models/ollama` | this session |
| `10-local-ai.conf` | ctx 16384, Flash Attention, q8_0 KV, 1 parallel / 1 model | the kit's `--tune` step |

### 6. Fix the tool, keep the kit

`summarize-doc.py` was patched rather than worked around with `-m qwen2.5vl:7b` everywhere: the request now carries `"think": false` (ignored by non-thinking models) **and** falls back to the `thinking` text if a model still refuses to answer, so the summariser degrades instead of dying.

## Implementation

### Phase 0 — Access key for `pmpmt` (prerequisite)

```bash
ssh-keygen -t ed25519 -a 100 -N "" -C "pi-cos@$(hostname)" -f ~/.ssh/id_ed25519_lan-pmpmt
# ~/.ssh/config: Host lan-pmpmt → HostName 192.168.1.60, User pmpmt, IdentityFile, IdentitiesOnly yes
# install, append-only and idempotent, as root via pistore's sudo:
ssh lan-storage 'sudo -n bash -s' <<'EOF'
KEY='ssh-ed25519 AAAAC3NzaC1lZDI1NTE5AAAAIP1PRXaLXdoFXMq77x//doJzGe/S4cNelmJh15gqG9vm pi-cos@pmpmt-ThinkPad-T15-Gen-2i'
install -d -m 700 -o pmpmt -g pmpmt /home/pmpmt/.ssh
grep -qF "$KEY" /home/pmpmt/.ssh/authorized_keys || printf '%s\n' "$KEY" >> /home/pmpmt/.ssh/authorized_keys
chmod 600 /home/pmpmt/.ssh/authorized_keys; chmod go-w /home/pmpmt
EOF
```

Existing unrelated key (`utter-it droplet`) preserved; `~/.ssh/config` backed up before editing. Result: `ssh lan-pmpmt 'id'` → `uid=1000(pmpmt)`.

### Phase 1 — Driver: diagnose, replace the stack, verify live, reboot

```bash
ssh lan-storage 'sudo -n bash -s' <<'EOF'
apt-get update -qq
apt-get install -y dkms                                # 3.0.11-1ubuntu13 — was absent
apt-get install -y nvidia-driver-595-open              # 595.99.02, pulls nvidia-dkms-595-open
modprobe nvidia && modprobe nvidia_uvm                 # prove the build before rebooting
nvidia-smi --query-gpu=name,memory.total,driver_version,compute_cap --format=csv
EOF
# → NVIDIA GeForce RTX 3060, 12288 MiB, 595.99.02, 8.6
ssh lan-storage 'sudo -n systemctl reboot'
```

SSH returned ~40 s after the reboot. Post-boot state:

```
dkms status → nvidia/595.99.02, 7.0.0-42-generic, x86_64: installed
lsmod       → nvidia, nvidia_modeset, nvidia_uvm, nvidia_drm   (all autoloaded)
nvidia-smi  → 595.99.02, CUDA 13.2
```

### Phase 2 — Kit onto the server, drive from the laptop

```bash
rsync -a docs/{install-ollama-stack.sh,summarize-doc.py,INSTALL.md,rtx3060-local-ai-models.md} lan-pmpmt:~/ollama-stack/
ssh lan-storage "sudo -n bash -c 'cd /home/pmpmt/ollama-stack && bash install-ollama-stack.sh --dry-run --models \"nomic-embed-text\"'"
ssh lan-storage "sudo -n bash -c 'cd /home/pmpmt/ollama-stack && bash install-ollama-stack.sh --yes --models \"nomic-embed-text\"'"
```

Dry run first, then the real run with only the 274 MB embedding model: installs Ollama, creates the `ollama` system user, writes `10-local-ai.conf`, enables and starts the unit, pulls one small model. `ollama 0.40.14`.

### Phase 3 — Move the weights to `/home` before the bulk download

```bash
install -d -m 750 -o ollama -g ollama /home/models/ollama
systemctl stop ollama
cp -a /usr/share/ollama/.ollama/models/. /home/models/ollama/ && chown -R ollama:ollama /home/models/ollama
rm -rf /usr/share/ollama/.ollama/models
printf '[Service]\nEnvironment="OLLAMA_MODELS=/home/models/ollama"\n' \
  > /etc/systemd/system/ollama.service.d/05-models-dir.conf
systemctl daemon-reload && systemctl start ollama
```

`ollama list` still showed `nomic-embed-text` afterwards — the relocation was proven by the model surviving it, not by exit codes.

## Failures, Quirks and Honest Gaps

- **Kit smoke test always fails.** It requests a chat completion from `nomic-embed-text`, an embedding model, so `--yes` runs end with `ERR Smoke test request failed (model: nomic-embed-text)`. Cosmetic; the model is present and listable.
- **A duplicate photo was destroyed.** `IMG_0444` existed as `.png`/`.jpg`/`.webp`; the `.png` went in the first cleanup and the other two in the second, leaving **zero copies anywhere** under that home. Nothing was flagged before the last deletion. Recovery must come from the phone or a backup.
- **A shell-quoting bug wasted a scan.** Building `find` arguments inside an SSH double-quoted string let quotes become literal `"*.mp4"`, so the video count came back as 0 and a follow-up glob (`*.ts`) dumped thousands of TypeScript declarations. Fixed by passing scripts through `ssh host 'bash -s' <<'REMOTE'` with single-quoted patterns.
- **145 packages are not upgraded** on the server. Untouched deliberately — unrelated to the driver and it deserves its own window.
- **Password authentication is still enabled** on both server accounts; flipping to key-only is deferred until the keys have been in use for a while.
- **Ollama has no authentication.** Reachable only through `ssh -L 11434:127.0.0.1:11434 lan-pmpmt`; nothing was bound to the LAN.
