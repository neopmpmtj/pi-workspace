## Problem

The image→SVG technique from the previous turn worked, but it existed only as a one-off: two scripts in the agent home, nine positional arguments, preferred settings living in a chat transcript, and a verification step that was "render it, then look at the PNG" — done by hand six times during the session. Nothing about it was reusable, and nothing about it was checkable.

The ask was one line: *"create a skill /svg-photo-convert"*.

What "done" had to mean, given that the previous session's central lesson was *rendering catches what markup hides*:

1. a future session can convert **any** raster image to SVG without re-deriving parameters;
2. the result is **proved**, not asserted — a measured distance to the source and a non-zero exit code when it is not good enough;
3. the failure modes already paid for in this session (headless browser quirks, palette method, halo colours, flat-art anti-aliasing) are encoded, not remembered.

A skill that produced the same lovely SVG while leaving "is it any good?" as an opinion would have missed the point.

## Architecture / Design Decisions

### 1. A skill, not another runbook entry

| Option | Verdict |
| --- | --- |
| Extend `docs/runbooks/svg-rendering.md` | rejected — documentation does not fire; the model still has to remember to look |
| Add a ninth positional-argument script | rejected — the interface was already the problem |
| **Skill with a routing description + bundled scripts + references** | **chosen** — fires on the right phrasing, carries its tooling, loads detail only when needed |

### 2. Two scripts, one job each

`trace_svg.py` produces; `verify_svg.py` proves. They share nothing but a file path, which means the verifier is also useful on SVGs made by anything else — including the hand-drawn illustration, or an SVG that predates this skill.

### 3. Presets, with the old flags still reachable

| Preset | For | colors | eps | scale | blur | merge | chaikin | resample |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| `photo` | photographs, gradient artwork | 56 | 0.85 | 2 | 0.45 | 14 | 1 | lanczos |
| `graphic` | logos, flat art, icons | 32 | 0.55 | 2 | 0 | 6 | 1 | nearest |
| `text` | screenshots, UI, diagrams | 24 | 0.35 | 2 | 0 | 4 | 0 | nearest |

Every value stays overridable by its own flag. The presets exist because the right numbers depend on the *kind* of source, and asking a caller to rediscover that is exactly the failure mode this skill removes.

### 4. Upsampling follows the content — measured, not reasoned

The first icon trace, using the photo path's LANCZOS upsampling, produced **17 layers and MAE 8.2** from a two-colour icon: LANCZOS at 2× manufactures a gradient of near-reds along every edge, and the tracer faithfully traced all of them. Switching flat presets to NEAREST produced **3 layers and MAE 0.9** on the same file. Colour-exactness beats smoothness when the source has no gradients to smooth.

### 5. Verification returns a number, calibrated on real output

`verify_svg.py` renders the SVG headless and reports MAE, RMSE, p95 and the fraction of pixels off by more than 40 (0-255 scale), then exits non-zero unless the match is good. The bands were set from a measured sweep, not from intuition:

| colours | MAE /255 | RMSE | p95 | pixels off >40 | file |
| --- | --- | --- | --- | --- | --- |
| 8 | 37.3 | 68.1 | 199 | 26.2 % | 1.0 MB |
| 16 | 17.0 | 33.5 | 81 | 13.4 % | 1.4 MB |
| 24 | 12.9 | 20.8 | 52 | 10.0 % | 1.4 MB |
| 48 | 10.5 | 18.0 | 53 | 8.8 % | 1.8 MB |
| 96 | 11.7 | 21.2 | 60 | 12.2 % | 2.8 MB |

Two conclusions were written into the skill: a photographic trace **plateaus near MAE 10** (that is what flat-colour posterisation costs), and **more colours stops helping** past ~48-64 because the extra entries land in speckle. First-draft bands labelled the good 48-colour trace "acceptable"; they were recalibrated to 8 / 13 / 20 MAE so the reference output scores "good" and only real loss triggers a re-tune.

### 6. Warn, never silently re-tune

The tracer refuses only one thing automatically: supersampling past ~2.2 Mpx, where it reduces `--scale` and says so. Everything else is a printed warning (`file is too heavy`, `very dense geometry`) because a tool that quietly changes its own parameters cannot be reasoned about across runs.

### 7. `image-describer` deliberately not called

The user asked directly whether the skill sends the image for a description first. It does not, for three reasons: a trace needs pixels, not semantics, so a description cannot change one path; `AGENTS.md` forbids delegating an attached image to that sibling unless the user names it; and the call is a sibling chat turn whose report lands in a file that then has to be read anyway. The skill body says nothing about it. The case where a description *would* help — a drawn illustration needing an object inventory, or a model without vision — is recorded here rather than wired in.

## Implementation

### Phase 1 — Skeleton and tracer

```
skills/svg-photo-convert/
├── SKILL.md                 route choice, workflow, bands, pitfalls
├── scripts/trace_svg.py     quantise → boundary trace → simplify → SVG
├── scripts/verify_svg.py    render → measure → side-by-side → exit code
├── references/parameters.md algorithm, every flag, calibration, limits
└── evals/                   evals.json, logo.png, README.md
```

The tracer is the previous session's algorithm with a real CLI: `argparse`, presets, an exact-palette path for images with ≤ 256 colours, an alpha `clipPath`, the supersample guard, and `ET.parse()` as its own last step so unbalanced output fails at build time.

```bash
python3 scripts/trace_svg.py photo.jpg -o photo.svg
python3 scripts/trace_svg.py shot.png  -o shot.svg --preset text
python3 scripts/trace_svg.py logo.png  -o logo.svg --preset graphic --transparent
```

### Phase 2 — Verifier

Structural checks (parses, any `<image>`, external refs), a headless render at the SVG's **own declared size**, then `ImageChops.difference` → `ImageStat` for MAE/RMSE and a histogram for p95/%bad, a side-by-side PNG, and an optional 2× zoom crop produced by rewriting `width`/`height` in a temporary copy.

### Phase 3 — Calibration sweep

Ten renders (the table above plus the UI, icon and illustration cases), each measured and eyeballed. This is what turned "MAE 10.5 feels fine" into a defensible band and caught the non-monotonic colour curve.

### Phase 4 — Three bugs found only by running it

| Bug | Symptom | Root cause | Fix |
| --- | --- | --- | --- |
| relative screenshot path | five script runs in a row produced no PNG, Firefox exit code 0 | headless Firefox silently writes nothing when `--screenshot` gets a relative path | `os.path.abspath()` before rendering; documented as a pitfall |
| intermittent render failure | identical manual command worked, script failed three times running | a desktop Firefox instance for the same user breaks the headless CLI | `--no-remote`, a fresh throwaway profile per attempt, three retries with backoff |
| bogus 95.4 MAE on a transparent PNG | a visually fine logo scored "poor" | source compared with alpha flattened to black, render composited on white | `_flatten()` composites both onto white; the same file scored 14.8 |

A fourth, caught before it could fire: `dims()` in `svg_size()` returned a one-tuple because of a stray trailing comma, which would have thrown on the first real run.

### Phase 5 — Flat-art path and alpha

`--resample {lanczos,nearest}` driven by preset (see §4), plus alpha traced into a `<clipPath id="alpha">` and used to clip all layers, so a transparent logo ships with no opaque background rect. Verified: `0` `<rect>` elements, 3 distinct fills, `clip-path="url(#alpha)"` present.

### Phase 6 — Evals and self-test

`evals/evals.json` holds four prompts: photo→poster, screenshot→docs, transparent logo, and *"draw it instead"* (the route-selection failure mode no file-level assertion catches). Assertions are all mechanically checkable from the SVG plus the verifier's output. Because the harness has no subagents, every objective assertion was executed by hand and the results recorded in `evals/README.md`, with an explicit note that with-skill/baseline pairs and description optimisation remain unrun.

### Phase 7 — Wiring

- `prompts/svg-photo-convert.md` — the literal `/svg-photo-convert <image>` command, argument-hinted, which loads the skill and states the expected reporting.
- `docs/runbooks/svg-rendering.md` — now opens with "canonical implementation is the skill", keeping the session artefacts as history.
- `docs/INBOX.md` — one item under a new *Skills* section for the unrun eval loop and description optimisation.

## Failures, Quirks and Honest Gaps

- **No harness eval run.** This agent has no subagent tool and no `claude` CLI, so the skill-creator loop — parallel with-skill/baseline subagents, the HTML review viewer, `run_loop.py` description optimisation — could not execute. The self-test substitutes for it imperfectly: it proves the tooling works and the assertions hold, but not that *a fresh model reading only the description* would route correctly. Logged in `docs/INBOX.md`.
- **Quality bands are source-class-dependent.** MAE 10 is "good" for a photo and "poor" for a logo; the verifier reports an absolute number and names the likely cause, but the caller has to know which class it is looking at. The skill says so in two places.
- **Templated photographic faces remain the weak case.** At 48-64 layers the eyes and lashes survive; below ~24 they become patches. Nothing in the tool can add detail the palette cannot express.
- **The verifier's number can be fooled by blur.** A soft, low-contrast trace can score well on MAE while losing structure, which is why opening the side-by-side PNG is an instruction, not a suggestion.

## Next Steps (tracked in `docs/INBOX.md`)

- Run `evals/evals.json` through a harness that has subagents, both configurations, then grade programmatically.
- Optimise the frontmatter description with `run_loop.py` once the `claude` CLI is available.
- Re-measure the calibration table if the tracer's defaults ever change; the verdict bands are derived from it.
