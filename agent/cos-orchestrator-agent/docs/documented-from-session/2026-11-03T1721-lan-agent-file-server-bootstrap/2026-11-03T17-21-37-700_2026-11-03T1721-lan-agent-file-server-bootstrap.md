# LAN File Server Bootstrap & `lan-agent` — Setup & Implementation Report

**Date:** 2026-11-03
**System:** Ubuntu 24.04.5 LTS laptop (`pmpmt`), Pi v1.4.0, Node v24.21.0 via nvm; server `192.168.1.60` = Ubuntu 24.04.4 LTS, OpenSSH 9.6p1, Ryzen 5 5600X, 15 GB RAM, RTX 3060 LHR, pi 1.4.0 on Node v24.22.2
**Location:** `~/.pi/agent-lan-agent/lan-agent/` (new sibling), `~/.pi/agent-cos-orchestrator-agent/cos-orchestrator-agent/docs/` (runbooks, inventory, reference), `~/.local/bin/pi-lan-agent`, server paths `/home/pistore/storage`, `/home/pmpmt/.pi/agent/`, `/etc/sudoers.d/`

---

## Problem

The laptop had no storage tier and an idle desktop server on the LAN. The server had disk (378 GB on `/home`), a GPU, and SSH enabled, but no usable account for machine work, no key-based access, no agent, and no inventory of the 42 GB already sitting in `/home/pmpmt`. Four things were needed:

1. A sibling agent (working name `lan-agent`, launcher `pi-lan-agent`) that stores and retrieves files on the server over SSH/rsync, and that tells the user how to set the server up the first time.
2. Key-based access for an unprivileged account (`pistore`) whose home would be the storage root.
3. Storage on the large partition rather than the 73 GB root filesystem.
4. `pi` installed on the server for the existing `pmpmt` user, so the server can host its own agent (API models now, local model once the 3060 driver works).

A constraint set the shape of everything: the server's address and target folder were expected to change (IP conflicts, DHCP moves, "may have to swap target folder"), so neither could be hardcoded anywhere.

## Investigation / Root Cause

### 1. Server identity and capability probe (read-only)

| Probe | Result | Consequence |
| --- | --- | --- |
| `nc -z <ip> 22`, banner | `SSH-2.0-OpenSSH_9.6p1 Ubuntu-3ubuntu13.20` | Ubuntu 24.04 → Linux runbook branch, not NAS |
| `lscpu`, `free -g` | Ryzen 5 5600X (6C/12T), 15 GB | Enough for a 7B–14B local model |
| `lspci` | `GA106 [GeForce RTX 3060 Lite Hash Rate]` | GPU present |
| `nvidia-smi` | "couldn't communicate with the NVIDIA driver" | Driver/kernel module dead → local agent blocked |
| `df -hT`, `lsblk` | `/dev/nvme0n1p5` → `/` 73 G (33 G free); `/dev/nvme0n1p7` → `/home` 378 G (318 G free) | Storage belongs on `/home` |
| runtimes | docker 29.5.3, node 18, python3; no ollama, no nvcc | Docker later declined by the user for this work |

### 2. SSH authentication failure — the actual root cause

The key was offered and rejected: `ssh -vv` showed `Offering public key: … SHA256:QILJBaiLfKIDRBVRLYt8GJkMn6D6tjhtGn22iDfFvow` followed by `Authentications that can continue: publickey,password`. Ownership, modes and `ssh-keygen -lf` on the server all passed, and `journalctl -u ssh` showed **no entries at all** — which was the decisive clue, not an absence of evidence.

| Hypothesis | Evidence | Verdict |
| --- | --- | --- |
| Empty `authorized_keys` | `wc -l` = 1 | Rejected — but only because the user's shell had `echo` (the chat copy of the recipe omitted it; `ssh-ed25519 … > file` runs a nonexistent command and leaves a 0-line file) |
| Wrong bytes / CRLF | `ssh-keygen -lf` matched the client fingerprint | Rejected |
| Permissions / `StrictModes` | `pistore:pistore`, `.ssh` 700, file 600 | Rejected |
| **`AllowUsers` excluding the account** | `sshd -T` → `AllowUsers pmpmt`; sshd logs *nothing* for an allow-list rejection | **Confirmed** |

Fix: `AllowUsers pmpmt pistore` (space-separated; a comma would create a user literally named `pmpmt,`), then `sshd -t && systemctl reload ssh`. Reload, not restart.

### 3. Tooling traps found while installing pi on the server

| Symptom | Cause | Fix |
| --- | --- | --- |
| `nvm.sh: No such file or directory` → `/nvm.sh` | nested `sudo -iu … bash -lc 'export NVM_DIR=$HOME…'` through SSH loses `HOME` in the quoting | heredoc: `ssh host 'sudo -u pmpmt -H bash -s' <<'EOS'` |
| `bash -lc 'node -v'` still v18 after editing `.bashrc` | Ubuntu's `.bashrc` returns early for non-interactive shells, so a block appended at the end is never reached | put the PATH/nvm block in `.profile` as well |
| `nvm install` → `find: Failed to restore initial working directory: /home/pistore` | cwd belonged to another user | `cd /home/pmpmt` first |
| `pi` "No API key found for deepseek" with keys in `.env` | pi does not read `<agent-dir>/.env`; either the launcher exports vars or `auth.json` supplies them | `auth.json` key commands (below) |

## Architecture / Design Decisions

### 1. Configuration as data, in one file

`config/storage.json` is the single source of truth (`host`, `user`, `port`, `identityFile`, `remoteRoot`, `defaultSubdir`). `REPLACE_` values count as unset and the wrapper refuses to run. Both volatile values are one command to change:

```bash
scripts/storage.sh use --host <ip>     # rewrites config AND the Host lan-storage block in ~/.ssh/config
scripts/storage.sh use --root <dir>
```

Alternatives rejected: hardcoding the IP in scripts (breaks on DHCP move), an `.env`-style variable per field (no structure, no `use` command, no drift detection against `~/.ssh/config`).

### 2. A wrapper, not raw ssh/rsync

`scripts/storage.sh` (331 lines) is the only sanctioned path to the server: `config`, `use`, `check`, `df`, `ls`, `put`, `get`, `sync`, `rm`, `ssh`, `shell`. It pins `IdentitiesOnly`, `BatchMode`, `ConnectTimeout`, `LogLevel=ERROR`, resolves every remote path under `remoteRoot` (rejecting `..` and anything outside), and refuses to delete `remoteRoot` itself. Exit codes: `2` config incomplete, `3` TCP unreachable, `4` SSH/write failure.

### 3. Identity: one account, chosen by the user

| Option | Consequence | Outcome |
| --- | --- | --- |
| Separate `piadmin` + second key | Least privilege, per-key revocation | Rejected by the user: "no new user" |
| Blanket `NOPASSWD: ALL` on `pistore` | One unencrypted key = root on that box | **Chosen**; documented as accepted risk |
| Scoped sudo (service + read-only diagnostics) | Safe, but blocks file organisation | Implemented first, then superseded by the user's decision |

The scoped drop-in `/etc/sudoers.d/90-pistore-lan-storage` still exists and is now redundant; the blanket rule lives in `/etc/sudoers.d/99-pistore-full` (the `99-` prefix is deliberate — sudo applies the **last** matching rule).

### 4. Credentials: `.env` holds secrets, `auth.json` holds references

`providers.md` documents a `!`-prefixed command as an API key. That is the only supported indirection, so:

| Before | After |
| --- | --- |
| `auth.json` held three plaintext keys | `auth.json` holds `"key": "!$HOME/.pi/agent/key DEEPSEEK_API_KEY"` |
| Rotation = edit JSON | Rotation = edit `.env` only |
| Two copies risk | One secret file (`.env`, 600) + an 8-line reader (`key`, 700) |

`$HOME` expansion inside that command proves pi runs the key command **through a shell** — verified by the call succeeding, not assumed.

### 5. Report/runbook policy adopted in this session

`AGENTS.md` gained a rule: any script or step-by-step procedure produced in chat must also be written to `docs/runbooks/<topic>.md` (or `scripts/`), because these commands "almost never change" and the file is the durable copy. This report follows that rule.

## Implementation

### Phase 1 — Sibling agent via `agent-creator`

```bash
node --experimental-strip-types skills/agent-creator/scripts/scaffold.ts \
  --name lan-agent --tools "read,bash,write,edit" --copy-keys \
  --provider deepseek --model deepseek-flash --thinking low
```

Produced the standard sibling layout (isolated `.env` 600, SQLite ledger, `/ask`, `/usage`, launcher `~/.local/bin/pi-lan-agent`), auto-registered in CoS `APPEND_SYSTEM.md` (siblings: image-describer, lan-agent, sm-google-workspace, web-master), unit tests 18/18, typecheck clean, smoke test `OK`.

Then customised beyond the template:

- `config/storage.json` + `scripts/storage.sh` + `scripts/gen-ssh-key.sh`.
- `extensions/chat/index.ts`: new `/storage` command that shells out to `storage.sh` with a quote-aware `splitArgs`, prints stdout verbatim, and emits a single `[FAIL]` on failure. Zero model turn, zero tokens.
- `AGENTS.md` rewritten around "read the config, never invent it"; `docs/SETUP.md` (352 lines) is the first-run runbook; `docs/CALLING.md` states the plain-language call and explains why `/ask` cannot touch the server.
- `agent.json` call rewritten to `<task in plain language> …`, plus a matching exception bullet in CoS `APPEND_SYSTEM.md`.

### Phase 2 — Laptop key and server account

```bash
ssh-keygen -t ed25519 -a 100 -f ~/.ssh/id_ed25519_lan-storage -C "pi-lan-agent@pmpmt-laptop" -N ""
# server, as pmpmt:
useradd --create-home --shell /bin/bash pistore && passwd -l pistore
mkdir -p /srv/pi-storage && chown pistore:pistore /srv/pi-storage
install -d -m 700 -o pistore -g pistore /home/pistore/.ssh
echo '<pubkey>' > /home/pistore/.ssh/authorized_keys   # note: echo, or the file stays empty
```

`~/.ssh/config` gained a `Host lan-storage` block (600, previous file backed up), and `storage.sh use` was extended to rewrite that block's `HostName`/`User`, verified by moving to `192.168.1.99` and back.

### Phase 3 — Debugging to READY

After the `AllowUsers` fix:

```
config:  ok (pistore@192.168.1.60:22, root /srv/pi-storage)
tcp:     open 192.168.1.60:22
ssh:     key-only auth ok as pistore
write:   ok (/srv/pi-storage writable)
space:   /dev/nvme0n1p5 73G 37G 33G 53% /
status:  READY
```

Proof of transfer was `cmp`, not an exit code: 50 MB of `/dev/urandom` → `put` (20.9 MB/s) → `get` (35.0 MB/s) → byte-identical → `rm`.

### Phase 4 — Storage moved to the large partition

```bash
install -d -m 0750 /home/pistore/storage
rsync -a /srv/pi-storage/ /home/pistore/storage/      # source was empty; only the target changed
```

`storage.sh use --root /home/pistore/storage` → `check` READY on `/dev/nvme0n1p7` (318 GB free), round trip re-verified. Old `/srv/pi-storage` left in place, not deleted.

### Phase 5 — Sudo: scoped, then deliberately widened

1. Wrote and validated `/etc/sudoers.d/90-pistore-lan-storage` (reboot/poweroff, `systemctl status`, `df`, `findmnt`, `lsblk`, `ss`, `journalctl`), removed `pistore ALL=(ALL) NOPASSWD:ALL` from `/etc/sudoers`, verified both directions: `sudo -n df` works, `sudo -n cat /etc/shadow` and `sudo -n id` refused.
2. User then required full access ("you can do all"). Installing `99-pistore-full` needed a password, which is exactly the operation the scoped rule blocked — circular by design; `pmpmt` ran it once.
3. Verified `sudo -n id` → `uid=0(root)`.

### Phase 6 — Reboot verification

`sudo -n systemctl reboot` at 16:09:24; SSH answered again ~35 s later; `check` READY; a 5 MB round trip byte-identical (`ROUNDTRIP_OK_AFTER_REBOOT`). sshd autostart, key, account, folder and DHCP address all survived.

### Phase 7 — `pi` for `pmpmt` on the server

```bash
nvm install 24 && nvm alias default 24        # → v24.22.2
npm i -g @earendil-works/pi-coding-agent@1.4.0
```

Plus: `/home/pmpmt/.local/bin/pi` wrapper pinning the node path (verified under `env -i`), and PATH/nvm blocks appended to `.bashrc` **and** `.profile` (backups `*.bak.<epoch>`).

Credentials, final shape:

```
/home/pmpmt/.pi/agent/
├── .env       600  DEEPSEEK_API_KEY / GEMINI_API_KEY / OPENAI_API_KEY
├── key        700  awk reader: prints one named value from .env, non-zero on miss
└── auth.json  600  {"deepseek": {"type":"api_key","key":"!$HOME/.pi/agent/key DEEPSEEK_API_KEY"}, …}
```

All three providers answered with live calls (`ENVREF_OK`, `ENVREF_GOOGLE`, `ENVREF_OPENAI`) after the indirection replaced the plaintext keys.

### Phase 8 — Inventory before touching files

`/home/pmpmt` = 42 GB: `Documents` 14 GB (`All Documents` 8.3 GB, `.backup_PC_cache` 4.9 GB), `Downloads` 6.4 GB (`#Arquive_Downloads` 6.1 GB / 125 files with 33 Cursor installers across 14 versions), dev caches ~17 GB (`/home/pmpmt/.config/Cursor` 4.6 GB, `snap/code` 2.7 GB, `.cache` 2.6 GB), media 1.49 GB.

Batch A prepared as server-side manifests (`/home/pistore/storage/.manifests/`), nothing moved yet, awaiting go:

| Manifest | Files | Size | Destination |
| --- | --- | --- | --- |
| `stale-installers.txt` | 33 | 5.61 GB | `storage/installers/` |
| `backups.txt` | 4 | 6.64 GB | `storage/backups/` |
| `media.txt` | 18 | 1.49 GB | `storage/media/` |

Protocol for every batch: manifest → dry run → `rsync -a` → count/byte comparison → nothing deleted (trash directory only), every path logged for undo.

`agent-lan-agent` had been swept into the `~/.pi` workspace repo by the harness's automatic
"session work" commit, which put a nested repo's worth of files under a parent that also tracks
other agents. Split out:

| Step | Command | Result |
| --- | --- | --- |
| Untrack from `~/.pi` | `git rm -r --cached agent-lan-agent` + `agent-lan-agent/` in `~/.pi/.gitignore` | commit `0098c41`; 0 tracked files, 36 on disk untouched |
| Own repo | `git init -b main`, `.gitignore`, commit `c4e938a` | 32 tracked files |
| Remote | `gh repo create neopmpmtj/lan-agent --private --source . --remote origin --push` | private, branch `main`, pushed 17:28 |

Naming follows the sibling convention already on GitHub (`web-master`, `image-describer`,
`cos-orchestrator-agent`): the repo is `lan-agent`, the directory stays `agent-lan-agent/`.

Ignored and verified absent from the remote tree: `.env`, `auth.json`, `sessions/`, `logs/`,
`*.sqlite*` (the ledger), `models-store.json`, `node_modules`, `**/*.bak.*`. One non-obvious entry:
`node_modules` here is a **symlink** to CoS's modules, and the scaffold's `node_modules/` pattern
(trailing slash) matches directories only — the bare name is required or the symlink gets committed.
