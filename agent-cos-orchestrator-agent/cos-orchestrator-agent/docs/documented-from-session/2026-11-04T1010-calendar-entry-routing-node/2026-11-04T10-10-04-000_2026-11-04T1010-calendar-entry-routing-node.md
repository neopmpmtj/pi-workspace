# Calendar Entry Routing Node — Setup & Implementation Report

**Date:** 2026-11-04
**System:** Laptop `pmpmt-ThinkPad-T15-Gen-2i` (Ubuntu, Pi v1.4.0, Node v24.21.0 via nvm, Python 3.12, `gog` 0.34.0); classifier TypeSafe JEV `jev-latest` → `jev-1.14.0`; extractor `deepseek-flash` (`https://api.deepseek.com`)
**Location:** node `~/.pi/decision-nodes/calendar/` (`config.py`, `route.py`, `README.md`, `tests/test_calendar.py`, `verdicts.jsonl`); harness `~/.pi/agent-cos-orchestrator-agent/cos-orchestrator-agent/` (`extensions/calendar-router/index.ts`, `src/calendar-router.ts`, `src/global-config.ts`, `test/*.test.ts`, `settings.json`); switches `~/.pi/config.json`; docs `docs/runbooks/calendar-routing*.md`, `docs/INBOX.md`, `~/.pi/docs/pi-state-of-jev.md`

---

## Problem

A calendar sentence typed into the agent did nothing. Three separate gaps combined to make that true:

1. **The judgment existed, with no caller.** `~/.pi/jev-classifier/jev-classifier-multi/` already answers "is this a calendar entry?" — `calendar` matches when the phrase states the intention to make an entry **or** names a venue **and** a date **and** a time. Grepping every agent home found **no** extension, cron job, or script calling it.
2. **The routing code that existed was idle and answered a different question.** `~/.pi/decision-nodes/scheduler/` runs a gate `intent` with options `create` / `other`; its `router()` returns `do:calendar`, and nothing consumes it. Its systemd units are not installed and its input database (`~/.pi/dbs/user-inputs.sqlite`) is absent.
3. **The four visible input gates are annotation only.** `inputContainsEmail`, `inputContainsPath`, `inputContainsUrl`, `lessThanInputWords` are regex checks configured in `~/.pi/config.json`; they print a line and add labeled text to the prompt, and none of them detects a date, a time, or a venue.

Goal, in the user's words: type a definite calendar entry (venue, date, time) and have it classified, routed to the Google Calendar agent, and — once agreed — actually created, without the manual delegation that had to be done by hand.

## Investigation / Root Cause

All measurements below are live, on this host, on 2026-11-04.

### 1. Which classifier answers this question?

| Phrase | `scheduler` gate `judge.py` | multi CLI `calendar` class |
| --- | --- | --- |
| "Lunch at Cafe Nero on Friday at 1pm" | `other` 0.10 → **abstains** | matches |
| "Dentist appointment at Clinica do Douro on Thursday 12 February at 10:30" | `other` 0.14 → **abstains** | `true` 0.990, `venue_date_time` |
| "Book lunch at Cafe Nero on Friday at 1pm" | `create` 0.84 ✓ | matches |

The scheduler gate asks *is this a request to book?*; the multi CLI asks *is this a calendar entry?*. The input shape the user cares about is a **statement**, so the scheduler gate was the wrong brain. The multi CLI was chosen and never re-implemented.

Cost per classification, measured: **~260–400 ms**, `input_tokens 1053 / output_tokens 136` (one JEV request covering all three classes).

### 2. What can the calendar side actually do?

| Probe | Result |
| --- | --- |
| `gog calendar create --help` | `<calendarId> --summary --from --to --timezone --location`, RFC3339 only — **no natural-language date parsing** |
| `gog calendar create` idempotency | no `--event-id` / client-supplied id → duplicates cannot be prevented with an API key |
| `gog calendar freebusy primary --from … --to … -j` | `{"calendars":{"primary":{"busy":[…]}}}`; empty list = free |
| `gog calendar events primary --from … --to … -j` | `{"events":[{"id","summary","start":{"dateTime"},"htmlLink"}]}` |
| Granted scopes | `calendar`, `docs`, `drive`, `sheets` on the `default` client |

Consequence: something has to produce `summary`, `location`, `start`, `end` as fields, because JEV returns a verdict and a score, not fields.

### 3. Why the stub came first

JEV's calendar class answers *whether*, not *what*. Extracting fields, validating them, and choosing a confirmation policy were separate decisions the user had not made. The router therefore shipped with two destinations — the read implemented, the write as `pass` — so the screen and the log kept showing what was missing.

### 4. Two failure modes found only by running it

| Failure | Evidence | Root cause |
| --- | --- | --- |
| Chain never fired | `do:calendar:create skipped · route 1 did not run - refusing to write blind` despite a `FREE` read | `execute()` appended to a local `results` list; the row never carried the read's result into the next destination |
| Hook block missing; model re-ran the node; a duplicate event was created | nested session transcript: *"No hidden calendar-router block appeared, so the hook didn't run… I should run the node myself"*, plus two verdict entries 8 s apart | the node ran inside an async `input` handler, which raced `before_agent_start`; the injected message was built before the verdict existed |
| `route.py --json` printed a traceback instead of a verdict | `TypeError: Object of type datetime is not JSON serializable` | the resolved event (with `datetime` fields) was stashed on the row and the row was serialized as-is |

## Architecture / Design Decisions

### 1. The node, not a new classifier

| Option | Verdict |
| --- | --- |
| Add calendar questions to the `scheduler` node | **rejected** — its measured `create`/`other` evidence would be invalidated, and it answers a different question |
| Copy the calendar questions into a new node | **rejected** — duplicates a measured, user-owned CLI |
| **Call `jev-classifier-multi` from a new `calendar` node** | **chosen** — one brain, one place to fix it |

Node shape follows the existing seam: `config.py` is the variable part (router + destinations), `route.py` is the invariant caller (clean → classify → verdict → route → execute → log).

### 2. Two destinations, chained

The user asked whether a create would re-check and make the read redundant. Three shapes were weighed:

| Shape | Read cost | Can the read stop the write? | Verdict |
| --- | --- | --- | --- |
| Independent destinations | 1 read | no — they run blind to each other | rejected |
| Merge into one destination | 1 read | yes, but loses the two-step trace | rejected |
| **Chained: read first, write consumes its verdict** | 1 read | **yes** | **chosen** |

Implemented as a shared result list: `execute()` publishes `row["routes"]` before the loop, so `do:calendar:create` reads `do:calendar:gog`'s verdict. The resolved event is shared the same way (`row["event"]`), so the write cannot disagree with the window that was checked.

### 3. Read: sibling agent → fixed `gog` call

| | Before | After |
| --- | --- | --- |
| What ran | `pi-sm-google-workspace -p "…read-only question…"` — a full chat turn | `gog calendar freebusy primary --from --to` |
| Latency | 10.1 / 12.8 / 13.8 / 15.1 / 19.2 s (measured runs) | **0.3–0.5 s** |
| Tokens | a sibling model turn | none |
| Verdict | prose that had to be parsed (`FREE`/`BUSY`/`UNKNOWN` in the first lines) | structured JSON, `busy: []` = FREE |
| Failure | a hallucinated or hedged answer | a non-zero exit → `UNKNOWN` → no write |

Replacing the read forced the field extraction to move **into** it (a free/busy call needs a window). The write now consumes the read's fields instead of extracting again.

### 4. Fields: one model call is unavoidable

| Option | Rejected because |
| --- | --- |
| Ask JEV for the fields | it scores questions; it does not return values |
| Parse dates in Python | stdlib has no "next Friday at 1pm"; the node convention is stdlib only |
| `gog` date parsing | `--from/--to` are RFC3339 only |
| **One `deepseek-flash` JSON call, then validate** | **chosen** — ~1.5k in / 100 out (~$0.0002), ~2 s, and everything after it is deterministic |

Validation (`_validate`): `start_local` must parse; a bad or missing end becomes exactly 60 minutes; the slot must not be in the past; confidence ≥ 0.5; the summary must be non-empty; a blank location becomes `null`. `Europe/Lisbon` is attached with `zoneinfo`, so summer and winter offsets are correct.

### 5. Write policy: immediate, with two hard guards

The user chose "write immediately" (2026-11-04). Two guards make that safe without a confirmation step:

- **The read's verdict is the permission.** Only `FREE` writes; `BUSY`, `UNKNOWN`, a failed read, or a read that never ran all skip with a printed reason.
- **Idempotency by title.** Because `gog` has no client-supplied event id, `create_event()` lists the window first and skips when the same title (case-insensitive) is already there: `skipped · already on the calendar (<id>)`. A failed duplicate check does not block the write — free/busy already said FREE.

### 6. Hook placement: awaited hook, never a slow `input` handler

| Placement | Outcome |
| --- | --- |
| Work in `input`, block injected in `before_agent_start` | **raced** — verdict arrived after the run had started; the model re-did the work and created a second event |
| **Local surfaces: work inside `input`, return `action: "handled"`** | no run follows, so no race; no model turn at all |
| **Telegram: work inside the awaited `before_agent_start`, return the message** | the block always lands; one relay turn |

A handled input never reaches `before_agent_start`, so the work happens once. The verdict is cached per prompt for the path that does reach it.

### 7. Both surfaces finish without a model turn, delivery permitting

| Surface | How the answer reaches the user | Cost |
| --- | --- | --- |
| TUI / `pi -p` | trace + outcome printed by the extension, input `handled` | node work only |
| Telegram (`[telegram` prefix) | same text sent through `@llblab/pi-telegram/delivery` → `sendTelegramView`, scope `active-turn` then `instance`, then `handled` | node work only |

**Delivery fails closed.** If the bridge module is absent, not bound, or refuses the target, `sendTelegram` returns false, the input is **not** swallowed, and the turn relays the injected block. A Telegram message is never dropped on the floor.

## Implementation

### Phase 0 — Measure before building

Live JEV and `gog` probes (tables above) plus a grep proving nothing called the classifier. This decided the brain and the field strategy before any file was written.

### Phase 1 — The node, read implemented / write stubbed

`~/.pi/decision-nodes/calendar/` with the same shape as its siblings:

```
config.py   NODE_NAME, CLASSIFIER, DESTINATIONS, router()
route.py    clean → classify → verdict → route → execute → log (+ CLI)
tests/      offline unit tests
verdicts.jsonl   metadata only, never the utterance
```

Router:

```python
def router(row):
    if row.get("abstained"):  return ["escalate"]
    if not (row.get("calendar") or {}).get("is_match"):  return []
    return ["do:calendar:gog", "do:calendar:create"]
```

### Phase 2 — Harness hook

| File | Role |
| --- | --- |
| `extensions/calendar-router/index.ts` | `before_agent_start` / `input` handlers, trace printing |
| `src/calendar-router.ts` | spawns `route.py --json`, parses it, builds the trace, the hidden block, and the outcome lines |
| `src/global-config.ts` | `readCalendarRouter()` — `enabled`, `print`, `mode: "route" \| "dry"` |
| `~/.pi/config.json` | `"calendarRouter": { "enabled": true, "print": true, "mode": "route" }` |
| `settings.json` | `+extensions/calendar-router/index.ts` |

Parsing fails open: bad JSON, exit 2, a missing script, or a timeout all become `ok: false` and the turn proceeds untouched.

### Phase 3 — The write, chained

```python
def do_calendar_create(row):
    verdict, why = _gate(row)                    # reads do:calendar:gog's result
    if verdict != "FREE":   return _skip(why)
    event = row.get("event")                     # resolved by the read
    if not isinstance(event, dict):  return _skip("no resolved fields …")
    return create_event(event, row)
```

`create_event()` → duplicate guard → `gog calendar create primary -j --summary … --from … --to … --timezone Europe/Lisbon --location … --description <original phrase>` → parse the returned id and link.

First live run created a real event (`Barber appointment`, Thu 05 Nov 15:00, id `ijfa0gll9n8k99dqrhhj4vb7ok`), which was deleted afterwards.

### Phase 4 — Replace the sibling read

`do_calendar_gog` became: `extract_event()` → stash `row["event"]` → `gog calendar freebusy`. `freebusy_verdict()` maps the JSON to `FREE` / `BUSY` / `UNKNOWN`; an unreadable payload is `UNKNOWN`, which never writes.

Measured after the change: classification 299–401 ms, freebusy 0.3–0.5 s, create 0.6–0.9 s — a match end to end in **~3 s** instead of ~16 s.

### Phase 5 — Fix the two live bugs, add the guard

1. `execute()` now publishes the shared results list before running destinations (`row["routes"] = results`), which is what makes the chain real.
2. `main()` drops `row["event"]` before serializing (`datetime` is not JSON), which is what makes `--json` usable by the extension.
3. Duplicate guard added: `gog calendar events primary --from --to -j`, compare `summary` case-insensitively, skip with the existing id and link.

### Phase 6 — No model turn on either surface

`input` runs the node, prints trace + outcome and returns `{action: "handled"}` on local surfaces. Telegram prompts take the same path, but the text is delivered through the bridge's public API:

```ts
const module = await import(pathToFileURL(deliveryModule(env)).href);
for (const kind of ["active-turn", "instance"]) {
  const sent = await module.sendTelegramView({ text }, { scope: { kind } });
  if (sent?.ok) return true;
}
return false;
```

The delivery module path is `~/.pi/agent-cos-orchestrator-agent/cos-orchestrator-agent/npm/node_modules/@llblab/pi-telegram/dist/api/delivery.js` (overridable with `PI_TELEGRAM_DELIVERY` for tests). The bridge binds its runtime in a `globalThis` registry, so a separately imported copy still finds it.

## Failures, Quirks and Honest Gaps

- **The chain was broken and the tests did not know.** `execute()` appended to a local list, so the write saw no read. Found on the first live run that needed the write (`route 1 did not run - refusing to write blind`), fixed by publishing the shared list.
- **A duplicate event was created once.** The hook's work lived in an async `input` handler; the block was built before the verdict existed, so the model re-ran the node itself. Diagnosed by reading the nested session transcript, not the logs. Fix: work inside `input` + `handled` locally, and inside the awaited `before_agent_start` on Telegram. The duplicate guard was added in the same pass as a second line of defence.
- **`--json` crashed on `datetime`.** The resolved event travelled onto the row. Fixed by dropping it before serialization; the routes carry the reported fields.
- **A second run of the same phrase now reports `BUSY`.** Correct but confusing: the first run's own event is what makes the slot busy. This is also why the model must not re-run the node, and why the guard exists.
- **`has_date` alone is not evidence.** A non-calendar phrase ("how many tokens did I use yesterday") scored `has_date 0.98` and still classified `false` — the AND is doing the work. Worth remembering before loosening the rule.
- **The extraction call is outside the pi ledger**, because it runs outside a pi turn. Its token counts are recorded under `event.extract_usage` in `verdicts.jsonl`, not in `/usage`.
- **The duplicate guard matches titles only**; "Dinner with Rita" and "Rita dinner" in the same window would both be created.
- **Telegram delivery is unexercised here.** This home has no `TELEGRAM_BOT_TOKEN`, so the fallback is what runs on the laptop; the success path is covered by unit tests with a stub module and must be verified on the VPS.
- **VPS enablement is blocked on three installs**: `gog`, `TYPESAFE_API_KEY`, and a `git pull` (node + extension + `calendarRouter` section).
