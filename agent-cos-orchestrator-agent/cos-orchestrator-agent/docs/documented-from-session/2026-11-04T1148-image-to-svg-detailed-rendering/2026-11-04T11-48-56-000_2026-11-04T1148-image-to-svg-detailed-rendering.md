# Image → SVG Rendering: From Hand-Drawn to Traced — Implementation Report

**Date:** 2026-11-04
**System:** Laptop `pmpmt-ThinkPad-T15-Gen-2i` (Ubuntu 24.04.5 LTS, Pi v1.4.0, Node v24.21.0 via nvm, Python 3.12.3, Pillow 10.2.0); verification renderer: Firefox headless (`--new-instance --profile`)
**Location:** inputs/outputs `~/.pi/01test_image-vision-model.jpeg`, `~/.pi/01test_image-vision-model.svg`, `~/.pi/01test_image-vision-model.illustrated.svg`; generators `~/.pi/agent-cos-orchestrator-agent/cos-orchestrator-agent/scripts/{fruit_portrait_svg.py,photo_trace_svg.py}`; runbook `~/.pi/agent-cos-orchestrator-agent/cos-orchestrator-agent/docs/runbooks/svg-rendering.md`
**Trigger:** a request shaped `Describe this image in detail: target -> .svg rendering <path>` — the deliverable is not prose, it is an SVG that has to carry the image.

---

## Problem

The task was to render a supplied photograph as SVG. The source is a 423×635 JPEG (32,216 B): a studio portrait of a woman in a violet turban crowned with apples, grapes, pears, a lime and a lemon, in a Carmen Miranda / food-editorial key.

Two things had to be true at once: the file had to be genuine SVG (no embedded raster as the answer), and it had to carry enough detail that the picture survives. The first attempt satisfied the "genuine SVG" half and failed the "enough detail" half — 172 flat primitives, 13 KB, a poster that reads as a symbol of the photo rather than a rendering of it. The user's follow-up was one line: *"try again and insert more detail into the svg"*.

Consequence: either draw by hand, or write the tracer. No third option without `sudo apt install`, which this account cannot do silently.

### 2. Reading the source precisely instead of by eye

The first drawing pass was placed by eye and was wrong in ways that only became visible side by side. The second pass replaced eyeballing with measurement — 2.5×/3× crops for texture, and colour-mask scans per row for silhouette:

```python
def skin(p):   r,g,b = p[:3]; return r>120 and r-b>35 and r-g>10 and g>60
def purple(p): r,g,b = p[:3]; return b>70 and b>r+15 and b>g+10
```

Row scan output that changed the geometry (skin and purple x-ranges per row):

| y | skin x-range | purple x-range | reading |
| --- | --- | --- | --- |
| 250 | 81–261 | 62–251 | fabric still spans the crown |
| 260 | 71–155 | **161–239** | forehead exposed left of x≈158 |
| 300 | 55–190 | 197–269 | fabric edge has moved right |
| 350 | 48–223 | 230–289 | fabric edge at x≈226, cheek visible to 223 |
| 370 | 66–237 | 273–274 | fabric gone; face/neck below |

The turban edge crosses the face **diagonally**: `(158,258) → (185,292) → (205,318) → (226,342) → (245,358)`. The earlier drawings had the fabric as a horizontal cap with the face underneath, which is why they read as a swim cap. The same scan fixed the face silhouette (left edge x≈50–57 nearly vertical, chin at ≈(112,502), far cheek to x≈245), the eye centres (74,347) and (146,342), the nose tip (98,405), the mouth x 84–150 / y 436–462, and the earring at (258,425).

### 3. Why the hand-drawn version kept failing

Four rendered iterations of `fruit_portrait_svg.py` (13 KB → 72.6 KB → 83.7 KB → 78.8 KB, ~950 elements, ~50 individually shaded grape berries, per-eye lash sets, fabric turbulence, embroidery patterns, film grain). Each one was rendered and compared side by side with the source. The verdict after the fourth: the *geometry* was by then defensible, but the *rendering* of a human face made of flat shapes reads as a mask — the eye socket, the lid lash line and the brow have to be near-photographic to stop looking like a cartoon, and vector primitives do not get there in a reasonable number of iterations.

That is the honest reason the technique changed, not a shortcut: the request was for a detailed SVG, and a trace produces 48 flat-colour layers with real photographic detail in ~1 s of compute.

## Architecture / Design Decisions

### 1. Two pipelines, not one

| Pipeline | Cost to run | Output | Kept because |
| --- | --- | --- | --- |
| `fruit_portrait_svg.py` (drawn) | ~1 s, 897 lines of source | 79 KB, 956 elements, stylised illustration | it is the only artefact that encodes *understanding* of the image; the traced file encodes measurement |
| `photo_trace_svg.py` (traced) | ~1 s, 221 lines of source | 2.0 MB, 48 layers, faithful vectorisation | it is what "more detail" actually required |

Both were shipped. The traced file took over the primary filename `01test_image-vision-model.svg` (the file the request points at); the drawing moved to `01test_image-vision-model.illustrated.svg` rather than being deleted.

### 2. Quantisation method — measured, not assumed

Same source, 28 colours, palette compared directly:

| Method | Palette character | Purple present? | Chosen |
| --- | --- | --- | --- |
| `Image.MEDIANCUT` | washed / greyed, most entries near-white: `#ffffff #fafefe #fdfef6 #f8f6ec …` | barely (`#5c3d55`, muddy) | no |
| `Image.FASTOCTREE` | punchy, hue-preserving: `#c72d38 #533363 #744989 #865396 #ebdb54 …` | yes, four distinct violets | **yes** |

Median cut spent palette slots on empty white background and left the turban brown-violet. Octree kept the turban violet and the fruit saturated, which is what makes the trace read as the same picture.

### 3. The tracer, step by step

1. **Supersample ×2** (LANCZOS) so traced diagonals are not bound to source pixel steps; the SVG then declares `width="423" height="635"` with `viewBox="0 0 846 1270"` — displays at the source size, resolves at twice the detail.
2. **Blur 0.45 → median 3** — kills JPEG ringing without moving boundaries far.
3. **Octree quantise** to N colours.
4. **Merge near-identical palette entries** (RGB distance < 14). This is the fix for the pale halos that appeared around every fruit: JPEG edge ringing produces near-white palette entries distinct from the background white, which get traced as thin light slivers.
5. **Boundary tracing on the pixel grid**, one pass per colour, mask kept on the left (`above/below/left/right` neighbour tests emitting consistently oriented edge segments), then edges chained into closed loops through a `start → [ends]` dict.
6. **Douglas-Peucker** ε 0.85 px, on halves of each loop (split at the point farthest from the first).
7. **One Chaikin pass** — corner cutting, which is what turns pixel staircases into clean vector edges.
8. **One `<path>` per colour with `fill-rule="evenodd"`**, so holes need no separate handling.
9. **Layers emitted largest-area-first**, so small details (lashes, beads, berries) land on top.

### 4. Parameter search (all rendered and looked at)

| Run | Colours | ε | Scale | Method | Merge | Size | Verdict |
| --- | --- | --- | --- | --- | --- | --- | --- |
| t1 | 22 | 0.55 | 1 | median | – | 731 KB | faithful but muddy, blocky edges |
| tA | 26 | 0.70 | 2 | octree | – | 2.2 MB | purple correct, skin broke into white patches |
| tB | 34 | 0.60 | 2 | octree | – | 2.7 MB | better skin, still haloed |
| tC/tD | 40 / 56 | 0.65 / 0.60 | 2 | octree | – | 2.9 / 4.6 MB | face convincing at 2× zoom |
| tG | 64 | 0.70 | 2 | octree | 16 | 3.3 MB | halos reduced (64→48 layers) |
| **tH** | **56** | **0.85** | **2** | **octree** | **14** | **2.0 MB** | **shipped** — 48 layers, lashes/iris/lip gloss/turban folds intact |

### 5. Alternatives considered and rejected

| Option | Rejected because |
| --- | --- |
| Base64-embed the JPEG inside `<svg>` | not a vector rendering; the answer would be the input |
| Install potrace/ImageMagick | no `sudo`, no `pip3`; and the tracer is 221 lines and ~1 s |
| k-means quantisation in pure Python | 268k px × N centres per iteration in Python — minutes per iteration for a marginal gain over octree |
| Keep iterating the hand-drawn face | four passes showed the ceiling is facial rendering fidelity, not effort |

## Implementation

### Phase 1 — look, describe, draw (turn 1)

Read the JPEG with the `read` tool, described it in detail (composition, palette, lighting, styling, anatomy of the headdress), and hand-wrote a first SVG: 172 elements, 5 palette families, one radial gradient per fruit. Overwrote `~/.pi/01test_image-vision-model.svg`.

### Phase 2 — measure the source (turn 2)

Crops at 2.5×/3× for `crop_top`, `crop_face`, `crop_right`, `crop_bottom`, plus the per-row skin/purple mask scan (§2 above). Every coordinate in the generator traces back to one of those two measurements.

### Phase 3 — generator + render-verify loop

`scripts/fruit_portrait_svg.py` (897 lines) emits the drawing. The loop that made it usable: render with Firefox, **look at the PNG**, fix.

```bash
python3 scripts/fruit_portrait_svg.py /tmp/x.svg
mkdir -p /tmp/ffprof
firefox --headless --new-instance --profile /tmp/ffprof \
        --screenshot /tmp/x.png --window-size=423,635 file:///tmp/x.svg
```

Two bugs caught only by rendering:

| Bug | Symptom | Fix |
| --- | --- | --- |
| two `<g>` opened, never closed | Firefox XML parse error page (`mismatched tag`, line 414) instead of an image | close `fruit-back` / `fruit-mid`; added `ET.parse(out_path)` to the generator so unbalanced output fails at build time, not at render time |
| Firefox refusing to start | `Firefox is already running, but is not responding` | `--new-instance --profile /tmp/ffprof` |
| screenshot cropped to the top-left quadrant | trace SVG declares 846×1270, capture window was 423×635 | the `displayW` parameter: `width`/`height` = source size, `viewBox` = trace size; capture at the display size |

The drawing improved to the point where proportions and colour blocks matched, and stopped improving where faces stop improving.

### Phase 4 — the tracer

`scripts/photo_trace_svg.py` (221 lines), CLI:

```
photo_trace_svg.py <in> <out> [colors] [eps] [scale] [method] [chaikin] [blur] [displayW] [merge]
```

Runtime measured: **0.7 s** at 1×/22 colours, ~1–2 s at 2×/56 colours. Output is self-contained — no `href`, no external fonts, no embedded raster (verified: `grep -o 'href="[^"]*"'` returns nothing).

### Phase 5 — ship both, document the knobs

`docs/runbooks/svg-rendering.md` (76 lines): both pipelines, an argument table with "good values", the symptom→knob mapping (pale halos → raise `merge`; blotchy skin → raise `colors`, lower `eps`; file too big → lower `scale`, raise `eps`), the headless-Firefox recipe and the Pillow side-by-side comparison snippet.

## Lessons worth keeping

- **Measure the source with masks, not by eye.** One row scan replaced three rounds of guesswork about where the fabric edge sits.
- **Render and look at the PNG.** Two of three structural bugs in this session were invisible in the markup and obvious in the render.
- **Preserve the supersampled `viewBox`.** Tracing at 2× and declaring `width`/`height` at 1× gives 4× the geometric detail at the same display size.
- **Merge the palette before tracing.** JPEG ringing manufactures near-white entries whose only visible effect is pale halos on every edge.
- **Switching technique is a legitimate answer to "more detail".** The drawn file encodes understanding; the traced file encodes the picture. Shipping both, labelled, beat defending the weaker one.
